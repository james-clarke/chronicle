Your day, reconstructed. Work stored on disk, and nowhere else.

Chronicle runs quietly in the background. An algorithm groups your window activity, terminal work and commits into the tasks you were actually doing, then writes your standup, timeline and reports from that.

A closer look at what you did and how you did it. Timestamps, application usage, every session that went into it and a short summary, laid out for you. There whenever you need it.

Quick, easy reports.

Ask your own history.

The chat is a language model running inside the app: Qwen3 4B, quantised to 4 bits, loaded through llama.cpp and run on your CPU. It is 2.4 GB on disk, downloaded once on first run, and stays loaded between questions so the second answer is quicker than the first.

It knows nothing about you except what is in the database. When you ask a question, Chronicle works out the time range you mean ("this morning", "last Tuesday") and pulls the tasks and activity from that window. If there is no time in the question it runs a full-text search over your tasks and sessions instead and takes the twelve best matches. That text goes into the prompt, and the model writes an answer from it and nothing else.

The question, the context and the answer stay inside one process. There is no request to make, so there is nothing to intercept.

What it sees

How a morning turns into a task. Left is what happens at each step. Right is the same morning's actual data as it moves through.

  1. Sees

    A small background process notices which window is in front and when you step away. It records the app name, the window title and the process id, and nothing else: no keystrokes, no screenshots, no clipboard. Alongside that, it watches the git repos you list for checkouts and commits, reads the timestamps of your Claude Code sessions, and notices when the microphone opens.

    X11 active window and title · idle from XScreenSaver · git and mic polled every 20 s 
    09:51:07  focus   Google-chrome  ACME-11501 club team builder · Jira
09:58:40  focus   Terminator     ~/dev/contoso — git checkout
09:58:52  git     contoso         checkout ACME-11501
10:14:03  focus   Sublime_merge  contoso · 3 conflicts
10:31:20  claude  ~/dev/contoso   session on ACME-11501

  2. Groups

    Raw focus events are noisy, so they get folded into spans. A title that changes but stays mostly the same is one span. Anything shorter than five seconds is counted as switching, not work. Thirty minutes away closes the batch.

    title similarity ≥ 0.8 keeps a span · < 5 s = context switching · 30 min away closes a batch 
    span  09:51–09:58  Google-chrome   ACME-11501 … · Jira
span  09:58–10:14  Terminator      ~/dev/contoso
span  10:14–10:31  Sublime_merge   contoso · 3 conflicts
span  10:31–11:05  Terminator      ~/dev/contoso
batch 09:51–11:05  4 spans · 0 away · 3 switches

  3. Recognises

    Before any model runs, a set of plain rules takes a first pass every minute. A ticket key in a title or a branch name points at that ticket's task. A repo points at the task you last worked on in it. Something you have corrected before gets the same answer again. These are written as provisional, so the timeline fills in while you are still working.

    every 60 s · branch → ticket · repo → last active task · past corrections via FTS5 · confidence 0.5, source = prepass 
    prepass  09:51–11:05  → ACME-11501
         reason: branch ACME-11501 matches anchor task
         confidence 0.50  provisional

  4. Thinks

    When a batch closes, it is turned into a short digest: apps by time, sites visited, git and session activity, and a minute-by-minute line of what was in front. If a ticket tracker is connected, the ticket's summary goes in too. A language model running inside the app reads the digest and answers with tasks, each with a time range. The answer is constrained to a fixed shape, so it cannot wander. Those replace the provisional rows.

    digest ≤ 3000 tokens · Qwen3 4B Q4_K_M via llama.cpp, in-process, CPU · grammar-constrained JSON · 4096-token window 
    digest  apps      Terminator 50m · Sublime_merge 17m · Chrome 7m
        activity  checkout ACME-11501 · claude session contoso
        context   ACME-11501 club team builder (Jira)

model   { "task": "reviewing and testing club team builder",
          "project": "contoso", "ticket": "ACME-11501",
          "start": "09:51", "end": "11:05" }

stored  09:51–11:05  reviewing and testing club team builder
        confidence 0.90  source = derived

  5. Learns

    It will be wrong sometimes. When you rename, move or throw out a block, the correction is stored with the context it was made in: the app and the window title. The next pass reads those first. Throwing a block out of a task is remembered as a hard no, so the same guess is not made again. Loose time gets folded into runs you can assign in one go, with the task pre-filled from what you did last time.

    corrections table + FTS5 · rename / reassign / eject · read by the rules and the model on the next pass

  6. Writes

    The standup draft, the timeline, the task cards, the reports and the chat all read the same table of intervals. Nothing is computed twice and nothing is stored anywhere else.

    one SQLite file · ~/.local/share/chronicle/chronicle.db 
    standup   reviewed and tested the club team builder
          (ACME-11501, 1h14m)
timeline  09:51 ────────────── 11:05  club team builder
report    contoso · ACME-11501 · 1.23 h
chat      "what did I do before lunch?" → same rows
