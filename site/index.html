Your workday, written down for you. Kept on your machine, and nowhere else.

Chronicle runs quietly in the background. An algorithm groups your window activity, terminal work and commits into the tasks you were actually doing, then writes your standup, timeline and reports from that.

The day, as it happened.

Each task, broken down. Each week, added up.

Open any task for a closer look at what you did and how you did it: timestamps, the apps you were in, every session that went into it and a short summary. There whenever you need it.

The week rolls the same detail up. Deep work, longest stretch, how often you switched, how it compares with last week, and every task grouped by project with its share of the hours. No spreadsheet, no filling anything in.

Ask your own history.

Questions you cannot answer from memory. What was I doing Tuesday afternoon before the call? How much of this month went to the launch? What did I finish last week? Ask in plain words and get an answer with times attached, taken from what your computer actually saw.

The model that answers runs inside the app, on your CPU. It is 2.4 GB on disk, downloaded once on first run, and stays loaded between questions so the second answer is quicker than the first. It knows nothing about you except what is in the database.

When you ask, Chronicle works out the time range you mean and pulls the tasks and activity from that window. If there is no time in the question it searches your tasks and sessions for the best matches instead. That text goes into the prompt, and the model writes an answer from it and nothing else. The question, the context and the answer stay inside one process.

What it sees

A morning, from the first window to the standup line. Six steps, and the same morning's data at each one.

What happens What it looks like inside

  1. Sees

    A small background process notices which window is in front and when you step away. It keeps the name of the app and the title of the window: the document, the sheet, the tab, the call. That is the whole record. No keystrokes, no screenshots, no clipboard.

    Where it can, it also picks up the things that say what the work was: a call starting, a project folder you are working in, a ticket number in a tab.

    09:02:14  focus  Chrome   Q3 launch brief – Google Docs
09:31:40  focus  Slack    #launch-planning
09:40:05  focus  Zoom     Launch sync
09:40:11  call   microphone on
10:12:22  focus  Chrome   LAUNCH-241 Landing page copy – Jira
10:40:10  focus  Figma    Landing page v2

  2. Groups

    Raw focus events are noisy, so they get folded into spans. A title that changes but stays mostly the same is one span. Anything shorter than five seconds is counted as switching, not work. Half an hour away closes the batch.

    span   09:02–09:31  Chrome   Q3 launch brief – Google Docs
span   09:31–09:40  Slack    #launch-planning
span   09:40–10:12  Zoom     Launch sync · on a call
span   10:12–10:40  Chrome   LAUNCH-241 Landing page copy – Jira
span   10:40–11:15  Figma    Landing page v2
batch  09:02–11:15  5 spans · 32m on a call · 4 switches

  3. Recognises

    Before any model runs, a few plain rules take a first pass every minute. A window that looks like one you have filed before gets the same answer. Work in a project folder points at the last task in that folder. A ticket in the branch you checked out points at that ticket. These are written down as provisional, so the timeline fills in while you are still working.

    rules  09:02–09:31  → Q3 launch brief
       reason: matches a correction you made on Tuesday
               "Chrome · Q3 launch brief" → Q3 launch brief
       confidence 0.50  provisional

       09:31–11:15  no rule matched · waiting for the model

  4. Thinks

    When a batch closes, it is turned into a short digest: apps by time, sites visited, calls and other activity, and a minute-by-minute line of what was in front. If a ticket tracker is connected, the ticket's summary goes in too. A language model running inside the app reads the digest and answers with tasks, each with a time range. The answer has to fit a fixed shape, so it cannot wander. Those replace the provisional rows.

    digest  apps     Chrome 57m · Figma 35m · Zoom 32m · Slack 9m
        call     09:40–10:12
        context  LAUNCH-241 Landing page copy (Jira)

model   { "task": "landing page copy and launch brief",
          "project": "Q3 launch", "ticket": "LAUNCH-241",
          "start": "09:02", "end": "11:15" }
        { "task": "launch sync", "project": "Q3 launch",
          "start": "09:40", "end": "10:12" }

stored  2 tasks · confidence 0.90

  5. Learns

    It will be wrong sometimes. When you rename, move or throw out a block, the correction is stored with the context it was made in: the app and the window title. The next pass reads those first. Throwing a block out of a task is remembered as a hard no, so the same guess is not made again. Loose time gets folded into runs you can file in one go, with the task pre-filled from what you did last time.

  6. Writes

    The standup draft, the timeline, the task cards, the reports and the chat all read the same table. Nothing is worked out twice and nothing is stored anywhere else.

    standup   Yesterday: landing page copy and the launch brief
          (LAUNCH-241, 2h13m) · launch sync (32m)
timeline  09:02 ──────────────── 11:15  Q3 launch
report    Q3 launch · LAUNCH-241 · 2.2 h
chat      "what did I do before the launch sync?" → same rows
